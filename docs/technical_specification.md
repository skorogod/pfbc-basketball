# Техническое задание: Telegram-бот клуба PFBC

Версия 1.1 · 2026-10-04 (1.1: без сообщений бота в группе при вступлении, `/invite`; длительность и пересечения событий; админские команды — в личке)

**Статус реализации:** этапы 0 и 1 выполнены, этапы 2–4 не начаты — подробно в разделе 8.

## 1. Общие сведения
- Наименование: Telegram-бот PFBC (далее «Бот»).
- Заказчик: любительский баскетбольный клуб PFBC.
- Основание: [specification.md](specification.md).
- Цель: автоматизировать организационные процессы составов клуба (опросы, дежурства, поздравления, оплата, журнал событий) и сократить ручную работу тренеров и капитанов.

## 2. Термины
Состав, групповой чат состава, ABL ([ablforpeople.com](https://ablforpeople.com/)), mtgame ([mtgame.ru](https://mtgame.ru/) — сайт с профилями и статистикой игроков), топик (forum topic), сезон ABL, тренировка, матч, опрос, дежурные, квитанция, событие журнала, роли.

## 3. Роли и права
Роли привязаны к составу, кроме админа (он глобальный). Один пользователь может иметь разные роли в разных составах.

| Действие | Игрок | Капитан | Тренер | Админ |
|---|---|---|---|---|
| Регистрация, редактирование своего профиля | ✓ | ✓ | ✓ | ✓ |
| Ответ на опросы | ✓ | ✓ | ✓ | – |
| Замена дежурных | – | ✓ (свой состав) | ✓ | ✓ |
| Расписание тренировок, отмена/перенос | – | – | ✓ | ✓ |
| Ручной ввод/правка матча | – | ✓ | ✓ | ✓ |
| Запуск голосования о разборе игры | – | – | ✓ | ✓ |
| Дата оповещения об оплате | – | – | ✓ | ✓ |
| Персональный запрос квитанции | – | – | ✓ | ✓ |
| Журнал событий (CRUD) | – | ✓ | ✓ | ✓ |
| Поздравления с праздниками | – | – | – | ✓ |
| Управление составами, ролями, привязкой чатов/топиков | – | – | – | ✓ |

## 4. Функциональные требования

### ФТ-0. Контроль доступа: членство в группе состава — источник правды
- Бот работает **только** с пользователями, которые состоят хотя бы в одной привязанной группе состава. Исключение — глобальные админы из конфигурации (`ADMIN_TG_IDS`), они нужны для первоначальной настройки.
- **Источник правды — фактическое членство в Telegram-группе состава.** БД хранит его отражение (`squad_members.status`) и синхронизируется с ним:
  - `chat_member` со статусом `member`/`administrator`/`creator` → членство в составе становится `active`. Если пользователь новый, создаётся профиль со статусом `unregistered` и запускается онбординг (ФТ-1).
  - `chat_member` со статусом `left`/`kicked` → членство в этом составе становится `left`/`removed` и фиксируется `left_at`. Если у пользователя не осталось ни одного активного членства, его профиль получает статус `inactive`.
  - Повторное вступление восстанавливает членство и профиль; ранее введённые данные сохраняются.
- **Проверка на каждом апдейте.** Middleware `AccessMiddleware` стоит первым в цепочке и для каждого сообщения, callback и ответа на опрос проверяет пользователя по БД (один индексированный запрос):
  - есть активное членство (или пользователь — админ) → апдейт обрабатывается;
  - иначе апдейт отклоняется: команды, сообщения и нажатия кнопок не обрабатываются, ответы на опросы не учитываются. В личке бот один раз отвечает «Доступ только для участников команд PFBC» (с ограничением частоты), дальше молчит. Callback-и получают короткий `answerCallbackQuery` с отказом.
- **Пользователи, вступившие до подключения бота.** Bot API не отдаёт список участников группы, поэтому: если неизвестный пользователь пишет `/start`, бот проверяет его через `getChatMember` во всех привязанных чатах составов. Если пользователь найден, членство создаётся; если нет — отказ. Результат отрицательной проверки кешируется (например, на 10 минут) для защиты от флуда.
- **Сверка (reconciliation).** Worker раз в сутки проверяет `getChatMember` для всех активных членств: это страховка на случай пропущенных `chat_member`-апдейтов, например во время простоя. Расхождения исправляются в БД и попадают в `audit_log`.
- **Последствия удаления из группы:** пользователь исключается из опросов, очереди дежурств, поздравлений, напоминаний об оплате и журнала. Если он был капитаном или тренером, роль в этом составе снимается, админ получает уведомление. История (ответы, дежурства, квитанции) сохраняется для статистики.
- **Хранение ПДн после ухода:** профиль со статусом `inactive` хранится настраиваемый срок (по умолчанию 12 месяцев), затем ПДн обезличиваются: ФИО, дата рождения и mtgame удаляются, остаётся технический идентификатор для истории.
- **Обязательные условия для работы механизма:** бот — администратор каждой группы состава (без этого Telegram не присылает `chat_member`), а `chat_member` указан в `allowed_updates`.

### ФТ-1. Онбординг и регистрация
- При вступлении в группу бот **ничего не пишет в группу** (иначе при добавлении нескольких человек подряд группа засоряется) — только фиксирует членство (ФТ-0).
- Тренер, капитан или админ получает командой `/invite` ссылку `t.me/<bot>?start=reg_<squad_id>` и пересылает её новичку. Личное сообщение напрямую невозможно, пока пользователь сам не написал боту (ограничение Telegram).
- После `/start` в личке: информация о клубе и пошаговая анкета (FSM):
  1. ФИО (обязательно хотя бы имя);
  2. дата рождения (необязательна, но рекомендуется; без неё не будет поздравления);
  3. ссылка на профиль игрока на [mtgame.ru](https://mtgame.ru/) (необязательна; проверяется, что это URL с доменом `mtgame.ru` или его поддоменом);
  4. согласие на обработку персональных данных (обязательно; для несовершеннолетних — подтверждение законного представителя).
- Пользователь автоматически становится игроком того состава, из чьего чата пришёл. Тренер или админ может добавить его в другие составы.
- Команды `/profile` (посмотреть и изменить данные) и `/delete_me` (удалить персональные данные).

### ФТ-2. Тренировки и утренний опрос
- Тренер задаёт для состава шаблон расписания: день недели, время начала, длительность, зал.
- Исключения: отмена, перенос, разовая дополнительная тренировка.
- Каждый день в настраиваемое время (по умолчанию 09:00 МСК) для каждой тренировки дня публикуется неанонимный опрос «Придёшь на тренировку?» с вариантами «Да / Нет / Опоздаю» в топике «Тренировки».
- Ответы сохраняются (`poll_answer`). Тренер может запросить сводку командой или кнопкой.

### ФТ-3. Дежурные по залу
- В настраиваемое время перед тренировкой (по умолчанию за 3 часа) бот выбирает 2 дежурных.
- Алгоритм — очередь по давности последнего дежурства:
  - кандидаты — только ответившие «Да» на опрос дня;
  - из кандидатов исключаются новички: те, кто состоит в составе меньше 14 дней (срок настраивается) от `squad_members.first_joined_at`. При повторном вступлении после ухода льготный срок заново не начинается;
  - сортировка — **только по дате последнего фактического дежурства в этом составе**, самые давние первыми. Кто ещё ни разу не дежурил (после окончания льготного срока), идёт первым. При равенстве порядок случайный;
  - **количество дежурств не учитывается.** Игрок, который долго не ходил и вернулся, попадёт в дежурные первым, потому что давно не дежурил;
  - «Фактическое дежурство» — назначение со статусом `assigned`/`done`. Если дежурного заменили, дежурство ему не засчитывается и его место в очереди не меняется.
- Если кандидатов меньше двух, бот назначает тех, кто есть, а капитан получает в личку уведомление и назначает недостающих вручную.
- **В группе — одно объявление без кнопок** в топике «Тренировки»: упоминания дежурных и напоминание прийти за 15 минут. При любых заменах бот **редактирует это объявление**, а не пишет новые сообщения, — в группе всегда актуальный список и нечего случайно нажать.
- **Дежурному — в личку** назначение с кнопкой «🙅 Не могу дежурить». Так как правка сообщения не присылает уведомлений, назначенный после объявления (замена, ручной выбор) получает личное сообщение; если личка недоступна (не нажимал `/start` или заблокировал бота) — одно короткое упоминание в топике ответом на объявление.
- **Капитану (нет капитана — тренеру) — в личку** сводка о дежурных с кнопками «🔁 Заменить: …» и «✋ Выбрать вручную»; та же сводка — по команде `/duty`.
- **Любое изменение — в два шага**: кнопка → вопрос с подтверждением («Заменить Иванова? Следующий по очереди: Петров» / «Назначить Петрова?» / «Отказаться от дежурства?») → «Да» или «Отмена». Случайное нажатие ничего не меняет. Предлагаемый в вопросе кандидат и фактически назначенный совпадают.
- **Отказ дежурного**: кнопкой «Не могу дежурить» (ответ в опросе остаётся «Да») или ответом «Нет»/«Опоздаю» в опросе. В обоих случаях — автозамена следующим по очереди, капитан получает уведомление; если заменить некем — капитану список для ручного выбора.
- Снятый капитаном или тренером получает уведомление в личку. Заменённое назначение не засчитывается как дежурство: место в очереди не меняется. История дежурств хранится.

### ФТ-4. Матчи ABL и опрос участия
- **Парсер** (модуль-адаптер `MatchSource`) по расписанию (по умолчанию каждые 6 часов) читает ablforpeople.com и ищет матчи команд, привязанных к составам. Для каждого состава хранится идентификатор/название команды на сайте ABL.
- Новый матч → запись в БД (соперник, дата и время, зал/адрес, стадия сезона) → опрос «Сыграешь?» в топике «Игры».
- Изменения на сайте (перенос, смена зала) → правка записи и сообщение в топике.
- **Фолбэк.** Если к дедлайну (настраивается, по умолчанию четверг 20:00 МСК перед игровыми выходными) матч состава не найден или сайт недоступен, капитан и тренер получают в личку запрос «Матч не найден автоматически — введите вручную / игры нет». Ручной ввод — короткий диалог (FSM). Ручная запись имеет приоритет: парсер её не перезаписывает, только сигнализирует о расхождении.
- Ошибки парсинга (изменилась структура сайта) логируются, админ получает уведомление.
- Сезонная структура (квалификация → дивизион → круги → плей-офф) хранится как атрибуты матча (`stage`, `division`), чтобы потом можно было добавить статистику.

### ФТ-5. Голосование о разборе игры
- После матча тренер получает в личку предложение «Запустить голосование о разборе?». Кнопка также доступна командой.
- Опрос в топике «Игры» с вариантами по умолчанию (например, «Пн перед тренировкой / Другое время / Не нужен»); тренер может их изменить.
- Итог отправляется тренеру; по желанию создаётся событие в журнале (ФТ-9).

### ФТ-6. Поздравления с днём рождения
- Ежедневно в 10:00 МСК бот поздравляет каждого игрока, у которого сегодня день рождения, во всех его составах, в топике «Поздравления».
- Текст берётся из шаблонов (несколько вариантов, случайный выбор), шаблоны редактирует админ.
- Если день рождения 29 февраля, в невисокосный год поздравление 28 февраля.
- **Предупреждения тренеру и капитану.** За 7, 3 и 1 день до дня рождения игрока (настраивается: `birthday_staff_reminder_days`) тренер и капитан состава получают в личку сводку — одно сообщение со всеми ближайшими именинниками состава, в 10:00 по времени состава. О собственном дне рождения получатель не предупреждается. В сам день рождения — только сообщение в топик «Поздравления», в личку ничего не приходит. Каждое предупреждение отправляется ровно один раз.

### ФТ-7. Поздравления с праздниками
- Админ создаёт поздравление: дата и время, текст и медиа (необязательно), целевые составы (все или выбранные).
- Публикация в топике «Поздравления» по расписанию. Есть предпросмотр, правка и отмена до отправки.

### ФТ-8. Оплата тренировок (квитанции mos.ru)
- Тренер или админ задаёт для состава расписание оповещений: день месяца и время, либо разовую дату.
- Оповещение в топике «Оплата»: «Пришлите квитанцию об оплате тренеру».
- Игрок отправляет квитанцию (фото или PDF) боту в личку. Бот пересылает её тренеру(-ам) состава и отмечает статус «прислал» за период.
- Тренер видит список «не прислали» за период и может одним действием отправить персональные запросы: всем должникам или выбранному игроку. Если игрок не начал диалог с ботом, тренер видит предупреждение.
- Тренер может вручную отметить оплату (например, если квитанция пришла не через бота).

### ФТ-9. Журнал событий
- Тренер или капитан ведёт журнал событий состава (товарищеская игра, собрание, сбор, турнир…): тип, название, дата и время начала, **длительность**, место, описание. Матчи из ФТ-4 попадают в журнал автоматически (длительность матча — 120 мин).
- **Проверка пересечений.** При создании событие сравнивается с тренировками, матчами и другими событиями того же состава. Конфликт — пересечение интервалов по времени (встык — не конфликт). При конфликте бот показывает предупреждение со списком пересечений; пользователь может продолжить, изменить время или отменить. Без подтверждения событие с пересечением не создаётся (проверка — на стороне сервера).
- **Публикация.** При создании выбирается, публиковать ли событие в группе состава. Если да — пост в соответствующем топике (матч и турнир — «Игры», остальное — «Общий»), туда же идут напоминания для команды.
- `/events` — список ближайших событий доступных составов.
- Автоматические напоминания тренерам и капитанам состава в личку: за 3 дня, за 1 день и утром в день события. Интервалы хранятся как настройка, чтобы их можно было менять.

### ФТ-10. Администрирование
- В группе состава вызываются только разовые команды привязки: `/bind <название>` (группа ↔ состав) и `/bind_topic trainings|games|greetings|payments|general` внутри нужного топика — только так бот узнаёт ID группы и топика. Сообщение с командой бот удаляет, ответ присылает админу в личку.
- **Несколько админов.** Корневые админы задаются в `ADMIN_TG_IDS` (список через запятую); их права вычисляются из конфигурации и снимаются удалением ID и перезапуском, из бота их не снять — так система не останется без админа. Любой админ может назначить админом участника состава или снять назначенного через `/admins` (снять себя нельзя). Назначенный админ теряет права, если покидает все группы составов (ФТ-0); остальные админы получают уведомление.
- Всё остальное — в личке бота: обзор составов (`/squads`), админы (`/admins`), назначение ролей кнопками (`/roles`), глобальные настройки и настройки состава (`/settings`, `/set <ключ> <значение>` — область определяется по ключу, для настройки состава бот спрашивает состав), включение и отключение функций (feature flags), редактирование шаблонов текстов.
- Сначала всё управление идёт через бота. Веб-админка в первой версии не делается, но архитектура её допускает (см. 5.6).

## 5. Архитектура

### 5.1 Стек
| Слой | Технология |
|---|---|
| Язык | Python 3.12 |
| Telegram-фреймворк | aiogram 3.x (async, FSM, роутеры, middleware) |
| Веб-сервер webhook | aiohttp (встроен в aiogram) |
| БД | PostgreSQL 16 |
| ORM / миграции | SQLAlchemy 2.0 (async) + asyncpg, Alembic |
| Хранилище FSM | PostgreSQL (своё хранилище) или Redis; Redis опционален, в MVP его можно не использовать |
| Планировщик | отдельный процесс `worker` + APScheduler с job store в PostgreSQL |
| Парсинг | httpx + selectolax / BeautifulSoup |
| Конфигурация | pydantic-settings (`.env`) |
| Логи / ошибки | structlog (JSON), опционально Sentry |
| Качество | ruff, mypy, pytest + pytest-asyncio, testcontainers (Postgres) |
| Пакеты | uv (или poetry) |

### 5.2 Схема процессов
- **web**: принимает webhook от Telegram на `POST /tg/webhook/<secret_path>` и проверяет заголовок `X-Telegram-Bot-Api-Secret-Token`. Обрабатывает команды, FSM, опросы. Health-check — `GET /healthz`.
- **worker**: планировщик (опросы, дежурства, поздравления, напоминания, оповещения об оплате) и парсер ABL. Сообщения отправляет через тот же Bot API-клиент.
- **postgres**, **reverse-proxy** (Caddy с автоматическим TLS Let's Encrypt).
- web и worker не зависят друг от друга по состоянию: всё общее состояние хранится в БД.

### 5.3 Слоистая структура кода
```
src/pfbc_bot/
  config.py              # pydantic-settings
  main_web.py            # точка входа webhook
  main_worker.py         # точка входа планировщика
  db/                    # engine, session, base, модели
  repositories/          # доступ к данным (только SQL)
  services/              # бизнес-логика, без зависимости от aiogram
  integrations/
    telegram/            # обёртка над отправкой (rate-limit, retry)
    abl/                 # MatchSource: интерфейс + AblWebsiteSource
  bot/
    routers/             # по модулю: registration, trainings, duty, matches,
                         # reviews, greetings, payments, events, admin
    middlewares/         # access (членство, первый в цепочке), db-session,
                         # user-context, RBAC, logging
    filters/             # role filters
    keyboards/, states/
  scheduler/
    jobs/                # одна задача = один файл, вызывает services
  texts/                 # шаблоны сообщений (подготовка к i18n)
migrations/  tests/  deploy/
```
Правила развития:
- Хэндлеры тонкие и вызывают только сервисы. Сервисы ничего не знают о Telegram и тестируются отдельно.
- Новая функция = новый роутер + сервис + задачи + миграция; остальные модули не меняются.
- Внешние источники данных (ABL, в будущем mtgame или mos.ru) подключаются через интерфейсы-адаптеры.
- Все тексты вынесены из кода: в шаблоны, а редактируемые — в БД.

### 5.4 Модель данных (основные таблицы)
- `users` — tg_user_id (unique), username, full_name, birth_date, mtgame_url, pd_consent_at, is_admin, dm_available, status (`unregistered`/`active`/`inactive`/`anonymized`), inactive_since, created_at.
- `squads` — name, age_group, abl_team_ref, is_active, timezone.
- `squad_members` — членство (отражение группы): user_id, squad_id, status (`active`/`left`/`removed`), first_joined_at (не перезаписывается при повторном вступлении), joined_at, left_at, last_verified_at; unique(user, squad).
- `squad_roles` — user_id, squad_id, role (`player`/`captain`/`coach`); роль действует, только пока членство `active`.
- `squad_chats` — squad_id, chat_id; `squad_topics` — squad_id, purpose, message_thread_id.
- `training_schedules` — squad_id, weekday, start_time, duration, venue, valid_from/to.
- `trainings` — материализованные экземпляры: squad_id, starts_at, venue, status (planned/cancelled/moved), source (schedule/manual).
- `matches` — squad_id, opponent, starts_at, venue, stage, division, source (parser/manual), external_id, manual_override, raw_payload jsonb.
- `polls` — type (training/match/review/custom), squad_id, ref_type/ref_id, tg_poll_id, chat_id, message_id, options jsonb, closes_at.
- `poll_answers` — poll_id, user_id, option_ids, answered_at.
- `duty_assignments` — training_id, user_id, status (assigned/replaced/done), assigned_by.
- `greetings` — kind (birthday_template/holiday), text, media, target_squads, send_at, status.
- `payment_reminders_config` — squad_id, cron/rrule, next_run_at; `payment_periods`; `payment_receipts` — user, squad, period, file_id, status, received_at.
- `events` — squad_id, title, type, starts_at, place, description, created_by, notify_group.
- `reminder_log` — уникальный ключ (kind, ref_id, offset) для идемпотентности: одно напоминание не отправляется дважды.
- `settings` — scope (global/squad), key, value jsonb; `feature_flags`.
- `audit_log` — кто, что и когда изменил.

Время хранится в `timestamptz` (UTC), пользователям показывается в Europe/Moscow.

### 5.5 Планировщик и надёжность
- Задачи идемпотентны: перед отправкой проверяется `reminder_log`, ключ уникальный.
- При рестарте пропущенные задачи догоняются, если не устарели (misfire grace, например 1 час для опросов и 12 часов для поздравлений).
- Отправка соблюдает лимиты Telegram (~20 сообщений в минуту в группу, ~30 в секунду всего): retry с учётом `retry_after`.
- Таймзона планировщика — Europe/Moscow.

### 5.6 Задел на развитие
- Сервисный слой можно открыть через REST (FastAPI) для будущей веб-админки или Telegram Mini App без переписывания логики.
- Тексты централизованы, поэтому i18n добавляется легко.
- Будущие модули: статистика посещаемости и игр, интеграция с mtgame.ru (подтягивать статистику игрока по ссылке на профиль через адаптер в `integrations/mtgame/`), учёт оплат, ростеры на матч, экспорт в Google Sheets.

## 6. Нефункциональные требования
- **Производительность:** ответ на команду < 1 с (p95) при нагрузке до ~500 пользователей и ~20 составов.
- **Доступность:** автоматический перезапуск контейнеров (`restart: unless-stopped`). Простой при деплое — не больше 1 минуты: Telegram повторяет доставку webhook, апдейты не теряются.
- **Безопасность:** секреты только в `.env`/переменных окружения, не в git. Секрет webhook и случайный путь. Postgres не доступен извне. SSH только по ключам, firewall (ufw: 22, 80, 443). Права проверяются на сервере для каждого действия.
- **Персональные данные:** согласие на обработку, удаление по запросу, минимум собираемых данных, данные детей — с согласия представителя. ⚠️ **Риск 152-ФЗ:** ч. 5 ст. 18 требует, чтобы первичная запись и хранение ПДн граждан РФ велись в базах на территории РФ. Иностранный VPS с ФИО и датами рождения этому требованию формально не соответствует. Заказчик должен решить это до запуска: например, держать БД на российском хостинге, а бот — на иностранном VPS, либо осознанно принять риск.
- **Логирование:** JSON-логи без ПДн в открытом виде, ротация. Об ошибках уведомляется админ.
- **Резервное копирование:** ежедневный `pg_dump` с хранением 14 дней и копией вне VPS (S3-совместимое хранилище). Восстановление проверяется раз в квартал.
- **Качество кода:** покрытие тестами сервисного слоя ≥ 70 %. Линтеры и тесты в CI обязательны.

## 7. Развёртывание
- Docker Compose: `caddy`, `web`, `worker`, `postgres`, `backup`.
- Миграции Alembic применяются при старте (`alembic upgrade head`) отдельным одноразовым сервисом.
- Webhook регистрируется при старте `web` через `setWebhook` с `secret_token` и `allowed_updates` (message, callback_query, poll_answer, chat_member, my_chat_member).
- CI/CD (GitHub Actions): lint → typecheck → tests → сборка образа → деплой по SSH (`docker compose pull && up -d`).
- Окружения: `dev` (локально, polling-режим для удобства) и `prod` (webhook).
- Требования к VPS: 1–2 vCPU, 2 ГБ RAM, 20 ГБ SSD, Ubuntu 24.04, публичный IP и домен.

## 9. Приёмка
Для каждого ФТ — сценарий проверки в тестовой группе-форуме:
- посторонний пользователь пишет боту → отказ, команды не выполняются;
- участника удаляют из группы → его профиль помечается в БД, команды и ответы на опросы больше не принимаются; после возвращения в группу доступ восстанавливается;
- участник, вступивший в группу до подключения бота, проходит проверку через `getChatMember` при `/start`;
- новый участник в группе не вызывает сообщений бота; по ссылке из `/invite` проходит регистрацию;
- событие, пересекающееся с тренировкой, вызывает предупреждение; встык — нет; опубликованное событие появляется в нужном топике;
- опрос появляется в нужном топике в нужное время;
- дежурные назначаются по давности последнего дежурства (вернувшийся после долгого перерыва игрок выбирается первым), новички первых 14 дней не назначаются, замена работает;
- при недоступном сайте ABL срабатывает фолбэк;
- напоминания журнала приходят за 3 дня, за 1 день и в день события ровно по одному разу, в том числе после рестарта worker;
- квитанция пересылается тренеру, статус меняется.

Критерии: все сценарии пройдены, CI зелёный, бэкап восстановлен на тестовом стенде.
