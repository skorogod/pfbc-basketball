# Техническое задание: Telegram-бот клуба PFBC

Версия 1.1 · 2026-10-04 (1.1: без сообщений бота в группе при вступлении, `/invite`; длительность и пересечения событий; админские команды — в личке)

**Статус реализации:** этапы 0 и 1 выполнены, этапы 2–4 не начаты — подробно в разделе 8.

## 1. Общие сведения
- Наименование: Telegram-бот PFBC (далее «Бот»).
- Заказчик: любительский баскетбольный клуб PFBC.
- Основание: [specification.md](specification.md).
- Цель: автоматизировать организационные процессы составов клуба (опросы, дежурства, поздравления, оплата, журнал событий) и сократить ручную работу тренеров и капитанов.

## 2. Термины
Состав, групповой чат состава, ABL ([ablforpeople.com](https://ablforpeople.com/)), mtgame ([mtgame.ru](https://mtgame.ru/) — сайт с профилями и статистикой игроков), топик (forum topic), сезон ABL, тренировка, матч, опрос, дежурные, квитанция, событие журнала, роли.

## 3. Роли и права
Роли (игрок, капитан, тренер) привязаны к составу; админ — глобальный. Один пользователь может иметь разные роли в разных составах и быть админом.

**Что может пользователь, определяют права, а не роли.** Каждой роли назначен набор прав — общий для всех составов. Права в составе = объединение прав ролей пользователя в нём (права игрока есть у всех участников). Админ может всё всегда. Набор прав роли меняет админ командой `/permissions` (роль → функции ✅/▫️, «Сбросить по умолчанию»); изменения действуют сразу. Хранится в `settings` (scope `permissions`), значения по умолчанию — в коде.

| Право | Что даёт | Игрок | Капитан | Тренер |
|---|---|---|---|---|
| Расписание и тренировки | `/schedule`, `/trainings`, `/training_add`: шаблоны, разовые, отмена, перенос | – | – | ✓ |
| Опрос на тренировку вручную | `/poll` | – | ✓ | ✓ |
| Сводки «кто придёт» | `/attendance`: тренировки, игры, события (без оплаты) | ✓ | ✓ | ✓ |
| Дежурства по залу | `/duty`: замена, ручной выбор, исправление прошедшего | – | ✓ | – |
| Собрания команды | `/event_add`, `/event_del` для событий «Собрание» | – | ✓ | ✓ |
| Игры, турниры, разборы и прочие события | `/event_add`, `/event_del` для матчей, турниров, разборов, сборов, прочего; `/review` и предложение разбора после матча; `/tournaments`: привязка матчей, название, дивизион, стоимость игры | – | – | ✓ |
| Сбор денег за игру 🔒 | `/game_pay` и сводка по оплате в `/attendance` | – | – | ✓ |
| Приглашение новичков | `/invite` | – | ✓ | ✓ |
| Напоминание о квитанциях за тренировки | `/receipts`: опрос «Отправил» за месяц вручную, со своим сроком | – | – | ✓ |

**Закреплённые права (🔒).** «Сбор денег за игру» доступен только роли «тренер» (и админу): другой роли его не выдать ни через `/permissions` (строка с 🔒 не переключается), ни записью в БД — такое значение игнорируется. Сводку по оплате видят только тренер и админ.

Всем участникам без прав: регистрация, свой профиль, ответы на опросы, `/events`. Только админу (вне таблицы): составы, роли, админы, настройки, права, привязка чатов и топиков, поздравления с праздниками. Админские кнопки и кнопка `/invite` проверяют права при нажатии (подделанные данные кнопки отклоняются); изменение и просмотр настроек проверяются и в сервисе.

**Кому бот присылает сообщения, связанные с правами**, — тем, у кого есть соответствующее право в составе: предложение разбора после матча — «Игры, турниры…» (тренер), замены и нехватка дежурных — «Дежурства» (капитан), напоминания о событиях и сообщения об их отмене — по праву на тип события (о собрании — тренеру и капитану, об игре или турнире — тренеру). Нет никого с правом — админам-участникам состава, а если и их нет — корневым админам из `ADMIN_TG_IDS`. Предупреждения о днях рождения — тренеру и капитану.

## 4. Функциональные требования

### ФТ-0. Контроль доступа: членство в группе состава — источник правды
- Бот работает **только** с пользователями, которые состоят хотя бы в одной привязанной группе состава. Исключение — глобальные админы из конфигурации (`ADMIN_TG_IDS`), они нужны для первоначальной настройки.
- **Источник правды — фактическое членство в Telegram-группе состава.** БД хранит его отражение (`squad_members.status`) и синхронизируется с ним:
  - `chat_member` со статусом `member`/`administrator`/`creator` → членство в составе становится `active`. Если пользователь новый, создаётся профиль со статусом `unregistered` и запускается онбординг (ФТ-1).
  - `chat_member` со статусом `left`/`kicked` → членство в этом составе становится `left`/`removed` и фиксируется `left_at`. Если у пользователя не осталось ни одного активного членства, его профиль получает статус `inactive`.
  - Повторное вступление восстанавливает членство и профиль; ранее введённые данные сохраняются.
- **Проверка на каждом апдейте.** Middleware `AccessMiddleware` стоит первым в цепочке и для каждого сообщения и callback проверяет пользователя по БД (индексированные запросы). Ответ на опрос проверяет сам сервис опросов: голос учитывается, только если проголосовавший — активный участник состава этого опроса:
  - есть активное членство (или пользователь — админ) → апдейт обрабатывается;
  - иначе апдейт отклоняется: команды, сообщения и нажатия кнопок не обрабатываются, ответы на опросы не учитываются. В личке бот один раз отвечает «Доступ только для участников команд PFBC» (с ограничением частоты), дальше молчит. Callback-и получают короткий `answerCallbackQuery` с отказом.
- **Пользователи, вступившие до подключения бота.** Bot API не отдаёт список участников группы, поэтому бот находит таких участников, когда они себя проявляют:
  - пишет `/start` в личку — проверка через `getChatMember` во всех привязанных чатах составов;
  - отвечает в опросе бота, а членства в составе этого опроса у бота нет — проверка через `getChatMember` в группе опроса; если участник, членство создаётся и голос засчитывается;
  - пишет в группе состава — автор сообщения и есть участник, членство создаётся без запроса к Telegram (служебное «вышел из группы» не в счёт).
  В группу бот при этом ничего не пишет. Отрицательный результат проверки кешируется (10 минут) для защиты от флуда. Дата вступления найденного участника неизвестна, поэтому новичком (ФТ-3) он не считается: иначе после подключения бота вся команда 14 дней не попадала бы в дежурные. Пользователи, которые с момента подключения бота ни разу себя не проявили, боту неизвестны.
- **Сверка (reconciliation).** Worker раз в сутки проверяет `getChatMember` для всех активных членств: это страховка на случай пропущенных `chat_member`-апдейтов, например во время простоя. Расхождения исправляются в БД и попадают в `audit_log`.
- **Последствия удаления из группы:** пользователь исключается из опросов, очереди дежурств, поздравлений, напоминаний об оплате и журнала. Если он был капитаном или тренером, роль в этом составе снимается, админ получает уведомление. История (ответы, дежурства, квитанции) сохраняется для статистики.
- **Хранение ПДн после ухода:** профиль со статусом `inactive` хранится настраиваемый срок (по умолчанию 12 месяцев), затем ПДн обезличиваются: ФИО, дата рождения и mtgame удаляются, остаётся технический идентификатор для истории.
- **Обязательные условия для работы механизма:** бот — администратор каждой группы состава (без этого Telegram не присылает `chat_member`), а `chat_member` указан в `allowed_updates`.

### ФТ-1. Онбординг и регистрация
- При вступлении в группу бот **ничего не пишет в группу** (иначе при добавлении нескольких человек подряд группа засоряется) — только фиксирует членство (ФТ-0).
- Тренер, капитан или админ получает командой `/invite` ссылку `t.me/<bot>?start=reg_<squad_id>` и пересылает её новичку. Личное сообщение напрямую невозможно, пока пользователь сам не написал боту (ограничение Telegram).
- После `/start` в личке: информация о клубе и пошаговая анкета (FSM):
  1. ФИО (обязательно хотя бы имя);
  2. дата рождения (необязательна, но рекомендуется; без неё не будет поздравления);
  3. ссылка на профиль игрока на [mtgame.ru](https://mtgame.ru/) (необязательна; проверяется, что это URL с доменом `mtgame.ru` или его поддоменом);
  4. телефон (необязателен; принимается в любом привычном виде — `8 (999) 123-45-67`, `+7 999 1234567` — и хранится как `+79991234567`);
  5. согласие на обработку персональных данных (обязательно; для несовершеннолетних — подтверждение законного представителя).
- В `/profile` телефон можно изменить или удалить. Тренер (и админ) там же задаёт **реквизиты для сбора денег**: перевод по номеру телефона или на карту (номер карты проверяется по контрольной цифре) + банк. Реквизитов может быть до 5: в `/profile` → «Реквизиты» — список, «➕ Добавить», «✏️ Изменить», «🗑 Удалить» (с подтверждением); задаёт и меняет их только сам владелец. При вводе телефона для перевода свой телефон из профиля предлагается кнопкой. `/delete_me` удаляет и телефон, и реквизиты.
- **Телефон** выводится слитно (`+79991234567`) — так Telegram подсвечивает его: по нажатию — позвонить или скопировать.
- **Ссылки на людей в личке.** По username (`t.me/…`) открываются всегда; без username — только если человек писал боту (любое личное сообщение). Иначе Telegram показывает ссылку как обычный текст, поэтому бот выводит имя с пометкой «(не в боте)»; в группе упоминание работает всегда.
- Пользователь автоматически становится игроком того состава, из чьего чата пришёл. Тренер или админ может добавить его в другие составы.
- Команды `/profile` (посмотреть и изменить данные) и `/delete_me` (удалить персональные данные).

### ФТ-2. Тренировки и утренний опрос
- Тренер задаёт для состава шаблон расписания: день недели, время начала, длительность, зал.
- Исключения: отмена, перенос, разовая дополнительная тренировка. Отмена и удаление записи расписания — в два шага, с подтверждением. Отменить или перенести уже начавшуюся тренировку нельзя.
- Каждый день в настраиваемое время (по умолчанию 09:00 МСК) для каждой тренировки дня публикуется неанонимный опрос «Придёшь на тренировку?» с вариантами «Да / Нет / Опоздаю» в топике «Тренировки».
- **Ранняя тренировка** — начинается не позже 14:00 включительно по времени состава (`early_training_until`). На неё опрос публикуется накануне в 21:00 (`training_poll_eve_time`), чтобы все успели ответить до назначения дежурных. Ранней считается и тренировка, на которую дежурных пришлось бы назначать раньше утреннего опроса (например, при увеличенном `duty_lead_hours`).
- **Перенос тренировки** — команда получает новые сообщения, а не правки: сообщение о переносе в группе; опрос на старое время закрывается, на новое время публикуется новый опрос по обычным правилам (ответы в старом опросе больше ни на что не влияют); назначенные дежурные снимаются (каждому — личное сообщение) и назначаются заново по ответам на новый опрос, с новым объявлением.
- **Опрос вручную** (`/poll`, капитан, тренер, админ) — в два шага, с подтверждением; только до начала тренировки:
  - опроса ещё нет — публикуется сразу, не дожидаясь планового времени; планировщик на эту тренировку опрос больше не публикует;
  - опрос уже есть (от бота или ручной) — публикуется новый, прежний закрывается (`superseded_at`, `stopPoll`), ответы в нём больше ни на что не влияют; участники отвечают заново. Назначенные дежурные остаются, отказ в новом опросе — как обычно, автозамена;
  - ручной запуск и плановая публикация идут по очереди под блокировкой тренировки: если планировщик отправлял опрос в момент ручного запуска, действует ручной, а опрос планировщика закрывается;
  - при переносе тренировки опрос снова публикуется планировщиком по новому времени (или вручную).
- Ответы сохраняются (`poll_answer`). Тренер может запросить сводку командой или кнопкой.

### ФТ-3. Дежурные по залу
- В настраиваемое время перед тренировкой (по умолчанию за 3 часа) бот выбирает 2 дежурных. На раннюю тренировку (ФТ-2) — утром в 08:00 (`duty_morning_time`); если к этому времени дежурные уже не успевают прийти заранее, — по обычному правилу. Пока опрос на тренировку не опубликован, дежурные не назначаются.
- Алгоритм — очередь по давности последнего дежурства:
  - кандидаты — только ответившие «Да» на опрос дня. **Тренеры не дежурят никогда**: их нет среди кандидатов, их нельзя выбрать вручную или указать при исправлении записи, а назначенный тренером снимается с будущих дежурств (автозамена, как при выходе из группы);
  - из кандидатов исключаются новички: те, кто состоит в составе меньше 14 дней (срок настраивается) от `squad_members.first_joined_at`. При повторном вступлении после ухода льготный срок заново не начинается;
  - сортировка — **только по дате последнего фактического дежурства в этом составе**, самые давние первыми. Кто ещё ни разу не дежурил (после окончания льготного срока), идёт первым. При равенстве порядок случайный;
  - **количество дежурств не учитывается.** Игрок, который долго не ходил и вернулся, попадёт в дежурные первым, потому что давно не дежурил;
  - «Фактическое дежурство» — назначение со статусом `assigned` (тренировка ещё не началась) или `done` (тренировка состоялась: с её начала бот переводит назначения в `done`). Если дежурного заменили, дежурство ему не засчитывается и его место в очереди не меняется. При отмене тренировки назначения переходят в `cancelled` и тоже не засчитываются.
- Если кандидатов меньше двух, бот назначает тех, кто есть, а капитан получает в личку уведомление и назначает недостающих вручную.
- **В группе — объявление без кнопок** в топике «Тренировки»: упоминания дежурных и напоминание прийти за 15 минут. **При любой замене или ручном назначении бот пишет новое сообщение** («🔁 Замена дежурного: … → @новый»), ответом на объявление, — правка сообщения уведомлений не присылает, а замену должны увидеть. Само объявление при этом редактируется, чтобы список в нём оставался актуальным.
- **Дежурному — в личку** назначение с кнопкой «🙅 Не могу дежурить».
- **Капитану (нет капитана — тренеру) — в личку** сводка о дежурных с кнопками «🔁 Заменить: …» и «✋ Выбрать вручную»; та же сводка — по команде `/duty`. Если назначенный не получил ни личного сообщения, ни упоминания в группе, рядом с его именем — «⚠️ не получил(а) уведомление», чтобы капитан предупредил лично.
- **Выход из группы**: назначенный дежурный, покинувший группу, автоматически заменяется следующим по очереди; капитан получает уведомление.
- **Любое изменение — в два шага**: кнопка → вопрос с подтверждением («Заменить Иванова? Следующий по очереди: Петров» / «Назначить Петрова?» / «Отказаться от дежурства?») → «Да» или «Отмена». Случайное нажатие ничего не меняет. Предлагаемый в вопросе кандидат и фактически назначенный совпадают.
- **Отказ дежурного**: кнопкой «Не могу дежурить» (ответ в опросе остаётся «Да») или ответом «Нет»/«Опоздаю» в опросе. В обоих случаях — автозамена следующим по очереди, капитан получает уведомление; если заменить некем — капитану список для ручного выбора.
- Снятый капитаном или тренером получает уведомление в личку. Заменённое назначение не засчитывается как дежурство: место в очереди не меняется. История дежурств хранится.
- **Исправление прошедшего дежурства.** Если дежурного экстренно заменили, а бот об этом не знал, капитан, тренер или админ в течение 7 дней после тренировки исправляет запись. В `/duty` показываются недавние прошедшие тренировки с кнопками «✏️ Исправить: …». Дальше выбирается участник, который дежурил на самом деле, и правка подтверждается. Назначенному дежурство не засчитывается (`replaced`), фактическому — засчитывается (`done`). Уведомления не отправляются, правка пишется в журнал аудита.

### ФТ-4. Матчи ABL и опрос участия
- **Источник — mtgame.ru** (ablforpeople.com сам берёт данные оттуда). Адаптер `MatchSource` (`integrations/mtgame`) читает публичный JSON API, вход не нужен: `/api/v1/team/<id>/tournaments/` (идущие турниры) и `/api/v1/team/<id>/tournaments/<tid>/games/` (игры, включая черновик следующего тура без даты и зала). Состав привязывается к команде настройкой `/set mtgame_team_id <id>` (id из ссылки `mtgame.ru/team/<id>`); отключение — `features.match_sync`.
- Задача `match_sync` worker-а — тик каждые 30 минут и при старте, но mtgame опрашивается, только пока ищется следующая игра: поиск открывается в `match_search_weekday` / `match_search_time` (по умолчанию вторник 12:00 по времени состава — лига назначает дату обычно во вторник вечером) после начала последней сыгранной игры и закрывается, как только у следующей игры появилось время. Игр ещё не было — поиск открыт сразу. Флаг `features.match_monitoring` (по умолчанию выключен) — опрашивать на каждом тике и после того, как игра найдена: так ловятся переносы и отмены. Игра без даты пропускается. Когда у неё появляется время (обычно во вторник вечером), создаётся запись в `matches` и матч в журнале «<хозяева> — <гости>» (описание «<турнир>, тур N», 120 мин) с постом и опросом участия в топике match. Пересечения не проверяются: время назначает лига.
- Матч привязывается к турниру журнала состава: сначала — с тем же **дивизионом** (турнир mtgame — это дивизион ABL, например «Москвич»; сравнение без учёта регистра), затем — с совпадающим названием (одно содержит другое). Если тренер уже завёл матч вручную (±3 ч от времени из mtgame), запись источника привязывается к нему, второй пост и опрос не публикуются.
- Изменения на сайте: новое время → перенос, как `/event_move` (сообщение в топике, прежний опрос закрывается, публикуется новый); новый зал → сообщение «Новое место»; будущая игра пропала из расписания mtgame или у неё сняли дату → тренерам (право «Игры, турниры…») в личку предупреждение, один раз на матч, сам матч не удаляется — решает тренер (`/event_del`). Переносы и отмены видны только при включённом мониторинге. Матч, удалённый из журнала, не восстанавливается.
- Сбой источника → лог и сообщение админам, не чаще раза в сутки по составу.
- **Фолбэк.** Если к дедлайну (настраивается, по умолчанию четверг 20:00 МСК перед игровыми выходными) матч состава не найден или сайт недоступен, капитан и тренер получают в личку запрос «Матч не найден автоматически — введите вручную / игры нет». Ручной ввод — короткий диалог (FSM). Ручная запись имеет приоритет: парсер её не перезаписывает, только сигнализирует о расхождении.
- Сезонная структура (квалификация → дивизион → круги → плей-офф) хранится как атрибуты матча (`stage`, `division`), чтобы потом можно было добавить статистику.

### ФТ-5. Разбор игры
- Разбор назначает тренер или админ (право «Игры, турниры, разборы…»): команда `/review` (или `/event_add` → тип «Разбор игры»). Это событие журнала (ФТ-9) типа «Разбор игры».
- **Время по умолчанию** — за час до первой тренировки недели (пн–вс по времени состава); бот предлагает его кнопкой. Если первая тренировка этой недели уже прошла (или до неё меньше часа) — первая тренировка следующей недели. Можно ввести другие дату и время. Нет ближайших тренировок — время вводится вручную.
- Название по умолчанию — «Разбор игры» (кнопкой), можно ввести своё.
- При публикации в группе — пост и неанонимный опрос «Буду / Не смогу» в топике match. Сводка ответов — `/attendance`.
- **Предложение после матча.** Когда матч закончился (начало + длительность), тренеры состава получают в личку «Матч прошёл… Назначить разбор игры?» (нет тренера — админы). Один раз на матч; рассматриваются матчи, закончившиеся не позже 3 дней назад. Отключается флагом `features.review_offers`.
  - «Да, назначить разбор» → бот предлагает время по умолчанию (см. выше): «Да, <время>» / «Другое время» (ввод даты и времени) / «Отмена»; «Не нужно» — разбор не назначается.
  - После подтверждения создаётся событие «Разбор игры: <матч>» (60 мин) с постом и опросом «Буду / Не смогу» в топике match. По одному матчу — один разбор: повторное нажатие или второй тренер получают отказ «Разбор уже назначен».

### ФТ-6. Поздравления с днём рождения
- Ежедневно в 10:00 МСК бот поздравляет каждого игрока, у которого сегодня день рождения, во всех его составах, в топике «Поздравления».
- Текст берётся из шаблонов (несколько вариантов, случайный выбор), шаблоны редактирует админ.
- Если день рождения 29 февраля, в невисокосный год поздравление 28 февраля.
- **Предупреждения тренеру и капитану.** За 7, 3 и 1 день до дня рождения игрока (настраивается: `birthday_staff_reminder_days`) тренер и капитан состава получают в личку сводку — одно сообщение со всеми ближайшими именинниками состава, в 10:00 по времени состава. О собственном дне рождения получатель не предупреждается. В сам день рождения — только сообщение в топик «Поздравления», в личку ничего не приходит. Каждое предупреждение отправляется ровно один раз.

### ФТ-7. Поздравления с праздниками
- Админ создаёт поздравление: дата и время, текст и медиа (необязательно), целевые составы (все или выбранные).
- Публикация в топике «Поздравления» по расписанию. Есть предпросмотр, правка и отмена до отправки.

### ФТ-8. Оплата тренировок (квитанции mos.ru)
**Реализовано (опрос «Отправил», по аналогии со сбором за игру):**
- Раз в месяц в `receipt_poll_day` (1–28, по умолчанию 1) в `receipt_poll_time` (10:00) по времени состава бот публикует пост «Пришлите квитанцию об оплате тренировок за <месяц> тренеру: <тренеры>» и неанонимный опрос «Отправил / Отправлю позже». Топик — «Оплата» (`payments`), если не назначен — общий. Если бот был выключен в день опроса, он публикует его в течение суток, позже — нет. Настройки меняет админ (`/set`), отключение — `features.receipt_reminders`.
- Вручную — `/receipts` (право «Напоминание о квитанциях за тренировки», по умолчанию у тренера; админ может выдать его другим ролям через `/permissions`). Срок — по умолчанию (`receipt_deadline_hours`, 24 ч) или своя дата.
- **Опрос за месяц — один на состав** (`receipt_requests`, уникальность «состав + месяц»). Запущенный вручную отменяет публикацию по расписанию в этом месяце; повторный `/receipts` не публикует опрос, а показывает, кто отметил «Отправил». При одновременном ручном и плановом запуске остаётся один опрос, второй пост удаляется.
- После срока каждому участнику состава, кроме тренеров, кто не отметил «Отправил», — личное сообщение; кому не дошло — упоминание в группе. Сколько раз и как часто напоминать — настройки состава: первое напоминание в срок, следующие — через интервал (`receipt_reminder_count`, по умолчанию 1, 0 — не напоминать, до 10; `receipt_reminder_interval_hours`, по умолчанию 24, до 168). **С 00:00 до 08:00 по времени состава напоминания не отправляются** — переносятся на 08:00; если из-за сдвига два напоминания совпали, уходит одно. Каждое напоминание — один раз; пропущенное больше чем на 2 суток (бот был выключен) не догоняется. Итог тренеру не присылается: кто отметился, видно в опросе. Опрос не закрывается: «Отправил» можно отметить и позже. **Завершить сбор** — кнопка «🏁 Завершить сбор» (в `/receipts`, когда опрос месяца уже опубликован, с подтверждением): бот закрывает опрос в группе, напоминания прекращаются; открыть снова нельзя. Опрос бота в группе может закрыть только сам бот, поэтому только так; если Telegram всё же сообщит о закрытии опроса (обновление `poll`), напоминания тоже прекращаются. Завершённый сбор месяц не освобождает: новый опрос в этом месяце не публикуется.
- **Все отправили.** Как только каждый участник состава, кроме тренеров (капитан — тоже), отметил «Отправил», тренеры получают в личку «✅ Все прислали квитанции за <месяц>»; если ни одному не дошло (или тренер не назначен) — сообщение в группу, в топик «Оплата». Один раз на опрос месяца.

**Не сделано (исходный объём ФТ-8):**
- Игрок отправляет квитанцию (фото или PDF) боту в личку. Бот пересылает её тренеру(-ам) состава и отмечает статус «прислал» за период.
- Тренер видит список «не прислали» за период и может одним действием отправить персональные запросы: всем должникам или выбранному игроку. Если игрок не начал диалог с ботом, тренер видит предупреждение.
- Тренер может вручную отметить оплату (например, если квитанция пришла не через бота).

### ФТ-8a. Сбор денег за игру
Отдельный процесс, не связанный с оплатой тренировок по квитанциям (ФТ-8): другие команды, таблицы и правила.
- **Опрос участия в матче** — варианты «Буду (тренер)», «Буду (игрок)», «Буду (болельщик)», «Не буду». Это сигнал для тренера, а не список платящих: **платят игроки заявки** (см. ниже).
- **Состав набран.** Когда «Буду (игрок)» отметили `game_payment_squad_size` человек (по умолчанию 10; 0 — выключено), тренерам состава (право «Сбор денег за игру») и админам — участникам группы приходит в личку **одно** сообщение: матч, дата, число игроков и кнопка «💰 Начать сбор». Дальше число **меняется в этом же сообщении** (правка — Telegram о ней не уведомляет, тренера не дёргаем; внизу — «обновлено дд.мм чч:мм»), кнопка остаётся — даже если игроков стало меньше порога. Подсказки в сообщении: больше `game_roster_max` — «в заявку войдут не больше 12»; меньше порога — сколько не хватает; у турнира нет стоимости игры — сумму введёте сами. Обновляет задача worker-а раз в минуту: изменения за минуту — одной правкой, вернулось к прежнему числу — ничего; сообщения хранятся в `roster_notices` (рестарт не повторяет). Сообщение удалили (правка не прошла) — бот присылает новое и дальше правит его. Кнопка снимается, когда сбор начат, голосование закрыто, матч прошёл или удалён; если матч перенесли (новое голосование) — по нему новое сообщение.
- **«Начать сбор»** → «Голосование об участии будет закрыто — снова открыть его нельзя. Подтвердить?» → при подтверждении опрос участия закрывается (состав зафиксирован), кнопки во всех уведомлениях снимаются. Если сбор по игре уже объявлен — «Сбор уже объявлен», второй тренер его не перебивает (проверяется и при нажатии, и при публикации под блокировкой матча). Прервались — повторное «Начать сбор» продолжает с того же места. Получатель денег — сам нажавший (тренер или админ), это проверяется до закрытия опроса. Дальше — шаги ниже, без выбора получателя.
- **Заявка на игру** — источник истины для оплаты. Выбирается в обоих сценариях (кнопка и `/game_pay`): одно сообщение с переключателями «✅ / ▫️ имя». Сначала — ответившие «Буду (игрок)» в порядке ответа (последнего изменения), отмечены первые `game_roster_max` (по умолчанию 12); «➕ Добавить из состава» показывает остальных активных участников (они помечены « ·»). Больше `game_roster_max` отметить нельзя, пустую заявку — тоже. Сумма, напоминания, «все оплатили» и сводка считаются **только по заявке**: проголосовавший, но не включённый, не платит и не получает напоминаний; включённый без голоса — платит. Заявка хранится в `game_payment_players`; у сборов, созданных до её появления, игроки — ответившие «Буду (игрок)».
- **Создание сбора** — право «Сбор денег за игру» (по умолчанию тренер; админ — всегда), `/game_pay`: состав → матч (сыгранные за последние 2 недели и предстоящие на 2 месяца) → **заявка** → сумма с каждого игрока → срок оплаты (кнопка «До …» — срок по умолчанию `game_payment_deadline_hours`, 24 ч, меняет админ через `/set`; «Без срока» или своя дата и время) → **получатель денег** → его реквизиты (показываются полностью для проверки) → предпросмотр → «Опубликовать».
  - получатель — сам создающий или тренер/админ состава, **который сам указал реквизиты** в `/profile` (например, админ создаёт сбор, а деньги получает тренер);
  - **реквизиты пользователя задаёт и меняет только он сам**: у получателя показываются все его сохранённые реквизиты полностью, выбрать можно одни из них (на сервере проверяется, что это действительно его сохранённые реквизиты; иные — отказ); свои одни — «✅ Реквизиты подтверждаю», несколько — «✅ N. …»; для себя — ещё и «✏️ Задать реквизиты» (нет реквизитов — сразу ввод, свой телефон из профиля предлагается кнопкой). После ввода — «Сохранить эти реквизиты в профиле?»: «Да» — добавляются к своим (лимит 5 — сообщение, сбор продолжается без сохранения), «Нет» — используются только в этом сборе. Сами по себе реквизиты не запоминаются;
  - если матч относится к турниру со стоимостью одной игры, сумма с игрока предлагается кнопкой с расчётом: стоимость ÷ число игроков заявки, с округлением вверх до рубля («15 000 ₽ ÷ 11 = 1 364 ₽»);
  - предпросмотр показывает «Состав на матч» и пост — это повторное подтверждение реквизитов и суммы;
  - в топике match публикуются: **«🏀 Состав на матч»** — название матча, «🗓 вс, 18.10 · 12:30», «📍 место» и «🏆 турнир» (если известны), описание, «Игроки (N):» нумерованным списком по алфавиту, упоминаниями (включённые получают уведомление); затем пост сбора: событие со всей информацией, сумма, получатель (ссылка на профиль) и его реквизиты (номер — моноширинным, копируется нажатием), срок, «Платят игроки из состава выше (N)»; следом — неанонимный опрос «💰 Оплата игры «…»: сумма» с вариантами «Оплатил» и «Оплачу позже». Опрос с одним вариантом Telegram не принимает (минимум два), поэтому второй вариант — «Оплачу позже»; на напоминания он не влияет;
  - новый сбор по той же игре через `/game_pay` заменяет прежний: прежний опрос закрывается, прежний «Состав на матч» удаляется, напоминаний по прежнему не будет. Действующий сбор на матч — один (гарантируется и в БД);
  - сообщения публикуются до записи сбора: если Telegram не принял что-то из них, уже отправленное удаляется и сбор не создаётся; заявка перепроверяется (не больше `game_roster_max`, только активные участники состава);
- **Напоминания.** Когда срок прошёл, бот проверяет: каждому игроку заявки, кто не отметил «Оплатил», — личное сообщение с суммой и реквизитами; кому личное не дошло — упоминание в группе в топике match. Сколько раз и как часто напоминать — настройки состава: первое напоминание в срок, следующие — через интервал (`game_payment_reminder_count`, по умолчанию 1, 0 — не напоминать, до 10; `game_payment_reminder_interval_hours`, по умолчанию 24, до 168). **С 00:00 до 08:00 по времени состава напоминания не отправляются** — переносятся на 08:00; если из-за сдвига два напоминания совпали, уходит одно. Каждое напоминание — один раз; пропущенное больше чем на 2 суток (бот был выключен) не догоняется. Итог тренеру не присылается: кто отметился, видно в опросе. Сбор без срока не напоминает. **Завершить сбор** — кнопка «🏁 Завершить сбор» (в сводке `/attendance` по матчу, право «Сбор денег за игру», с подтверждением): бот закрывает опрос в группе, напоминания прекращаются; открыть снова нельзя. Опрос бота в группе может закрыть только сам бот, поэтому только так; если Telegram всё же сообщит о закрытии опроса (обновление `poll`), напоминания тоже прекращаются. Учитываются только активные участники состава.
- **Все оплатили.** «Все» — игроки заявки. Как только каждый из них отметил «Оплатил», получатель денег и создатель сбора получают «✅ Все игроки оплатили игру» (один раз на сбор; не дошло — тем, у кого право «Сбор денег»). «Оплатил» не из заявки не учитывается.
- **Сводка.** В `/attendance` по матчу к ответам опроса участия добавляется блок оплаты: сумма и срок, кто из заявки оплатил, кто нет, и кто отметил оплату, не будучи в заявке.

### ФТ-9. Журнал событий
- Журнал событий состава ведут: собрания — капитан и тренер, остальные события (игры, турниры, разборы, сборы, прочее) — тренер; админ — всё (типы: матч, разбор игры, сборы — выезд на сборы, турнир, собрание, прочее): тип, название, дата и время начала, **длительность**, место, описание. Матчи из ФТ-4 попадают в журнал автоматически (длительность матча — 120 мин).
- **Проверка пересечений.** При создании событие сравнивается с тренировками, матчами и другими событиями того же состава. Конфликт — пересечение интервалов по времени (встык — не конфликт). При конфликте бот показывает предупреждение со списком пересечений; пользователь может продолжить, изменить время или отменить. Без подтверждения событие с пересечением не создаётся (проверка — на стороне сервера).
- **Публикация.** При создании выбирается, публиковать ли событие в группе состава. Если да — пост в соответствующем топике (матч, турнир и разбор игры — `match`, остальное — «Общий»), туда же идут напоминания для команды.
- **Опрос участия.** К опубликованному событию сразу после поста добавляется неанонимный опрос (`polls`: ref_type `event`). Ответы принимаются только от участников состава. Если Telegram опрос не принял, событие и пост всё равно создаются. Удаление события закрывает его опрос.
  - матч — «Буду (тренер) / Буду (игрок) / Буду (болельщик) / Не буду» (type match; «Буду (игрок)» — сигнал тренеру о составе, платят игроки заявки, ФТ-8a);
  - разбор игры — «Буду / Не смогу» (type review);
  - турнир — отдельный опрос «Участвую / Не смогу» (type tournament): кто готов участвовать в турнире.
- **Период турнира.** Точная продолжительность не нужна: дата старта (`дд.мм.гггг` или «Дата пока неизвестна») и длительность — число дней (многодневный турнир) или «Сезон» (лига ABL). Дата старта может быть в прошлом (сезон уже идёт). Турнир не участвует в проверке пересечений — заняты в нём матчи. В постах и списках: «12.10.2026 – 14.10.2026 (3 дн.)», «сезон, с 01.09.2026», «сезон, дата старта уточняется». Напоминания по турниру — только когда известна дата старта.
- **Дивизион лиги** (необязателен, до 100 символов, например «Москвич») — шаг при создании турнира после стоимости игры (можно пропустить); по нему матчи mtgame находят турнир (ФТ-4). **Название и дивизион** меняются в карточке турнира в `/tournaments` (кнопки «Изменить название», «Изменить дивизион» / «Убрать дивизион»).
- **Стоимость одной игры турнира** (вся сумма за игру, необязательна) — шаг при создании турнира после длительности (можно пропустить); изменить или убрать — в карточке турнира в `/tournaments` (кнопка «Изменить стоимость игры»). Используется в сборе денег за игру (ФТ-8a): сумма с игрока = стоимость ÷ число игроков заявки (вверх до рубля).
- **Турниры и матчи.** Матч может относиться к турниру (`events.tournament_id` → турнир). При создании матча (`/event_add` → «Матч») сначала выбирается турнир — из незакончившихся турниров состава — или «Без турнира», затем данные матча; нет турниров — шаг пропускается. Позже связь меняет админ: `/tournaments` → турнир → отметить матчи своего состава (✅ привязан). У матча — не больше одного турнира; матч другого состава привязать нельзя. Удаление турнира из БД снимает связь (`ON DELETE SET NULL`). Название турнира показывается в информации о матче: `/events`, напоминания, сообщение об отмене, сводка `/attendance`, предложение разбора; в пост и опрос — если матч привязан к турниру на момент публикации.
- **Сводки.** `/attendance` (тренер, капитан, админ) — список тренировок и событий с опросом (от недели назад до двух месяцев вперёд); по выбранному — кто как ответил и кто не ответил (только активные участники состава).
- **Перенос** (`/event_move`, право на тип события) — только будущего события на будущее время; турнир — новая дата старта. Команда получает новое сообщение «🔁 Перенесено …» (старое → новое время), опрос участия закрывается и публикуется заново (время другое — ответы собираются заново), напоминания пересчитываются по новой дате. Сбор денег за игру при переносе сохраняется.
- **Публикация** выполняется после сохранения события; тренер видит фактический результат: опубликовано с опросом / пост есть, опроса нет / в группу опубликовать не удалось (событие сохранено).
- **Закрытие опросов.** Опрос участия (тренировка, событие) закрывается в момент начала — ответы сохраняются и видны в сводках. Опрос участия в матче закрывается и раньше — при публикации сбора денег за него: платят ответившие «Буду (игрок)», и состав игроков с этого момента не меняется. Опрос «Оплатил» по сроку не закрывается. Отмена тренировки закрывает её опрос; удаление матча закрывает его опросы и отменяет сбор денег за него.
- **Удаление** ещё не прошедшего события — новое сообщение «❌ Отменено» в том же топике (если событие публиковалось) и тренерам/капитанам в личку.
- `/events` — список ближайших событий доступных составов.
- Автоматические напоминания тренерам и капитанам состава в личку: за 3 дня, за 1 день и утром в день события. Интервалы хранятся как настройка, чтобы их можно было менять.

### ФТ-10. Администрирование
- В группе состава вызываются только разовые команды привязки: `/bind <название>` (группа ↔ состав) и `/bind_topic trainings|match|greetings|teambuilding|payments|general` внутри нужного топика — только так бот узнаёт ID группы и топика. Сообщение с командой бот удаляет, ответ присылает админу в личку.
- **Несколько админов.** Корневые админы задаются в `ADMIN_TG_IDS` (список через запятую); их права вычисляются из конфигурации и снимаются удалением ID и перезапуском, из бота их не снять — так система не останется без админа. Любой админ может назначить админом участника состава или снять назначенного через `/admins` (снять себя нельзя). Назначенный админ теряет права, если покидает все группы составов (ФТ-0); остальные админы получают уведомление.
- **Карточка участника** (только админ): `/member` → состав → участник — только просмотр; в `/roles` → состав → участник — та же карточка с кнопками смены ролей. Роли (и отметка «админ бота») и данные профиля — Telegram (username, id), регистрация, ФИО, телефон, дата рождения, mtgame, в составе с, реквизиты для сборов (только просмотр — меняет их сам участник), открыта ли личка с ботом; если ссылки на профиль нет — объяснение почему. У участника, который был в группе до подключения бота, дата вступления неизвестна (Telegram её не сообщает): в карточке — «В составе: до подключения бота»; в БД у него условная дата 01.01.2000, чтобы в дежурствах он не считался новичком.
- **Меню команд** у каждого пользователя своё — по его правам (обновляется при обращении к боту); `/help` показывает то же. Любая команда посреди незавершённого ввода прерывает его.
- Всё остальное — в личке бота: обзор составов (`/squads`; кнопка «👥 Участники» под каждым составом — список участников с ролями, отметкой админа и незарегистрированных), админы (`/admins`), назначение ролей кнопками (`/roles`), права ролей (`/permissions`, см. раздел 3), глобальные настройки и настройки состава (`/settings`, `/set <ключ> <значение>` — область определяется по ключу, для настройки состава бот спрашивает состав), включение и отключение функций (feature flags), редактирование шаблонов текстов.
- Сначала всё управление идёт через бота. Веб-админка в первой версии не делается, но архитектура её допускает (см. 5.6).

### 5.2 Схема процессов
- **bot**: принимает webhook от Telegram на `POST /tg/webhook/<secret_path>` и проверяет заголовок `X-Telegram-Bot-Api-Secret-Token`. Обрабатывает команды, FSM, опросы. Health-check — `GET /healthz`.
- **worker**: планировщик (опросы, дежурства, поздравления, напоминания, оповещения об оплате) и парсер ABL. Сообщения отправляет через тот же Bot API-клиент.
- **postgres**, **reverse-proxy** (Caddy с автоматическим TLS Let's Encrypt).
- bot и worker не зависят друг от друга по состоянию: всё общее состояние хранится в БД.

### 5.3 Слоистая структура кода
```
src/pfbc_bot/
  config.py              # pydantic-settings
  main.py                # точка входа webhook
  main_worker.py         # точка входа планировщика
  db/                    # engine, session, base, модели
  repositories/          # доступ к данным (только SQL)
  services/              # бизнес-логика, без зависимости от aiogram
  integrations/
    telegram/            # обёртка над отправкой (rate-limit, retry)
    abl/                 # MatchSource: интерфейс + AblWebsiteSource
  bot/
    routers/             # по модулю: registration, trainings, duty, matches,
                         # reviews, greetings, payments, events, admin
    middlewares/         # access (членство, первый в цепочке), db-session,
                         # user-context, RBAC, logging
    filters/             # role filters
    keyboards/, states/
  scheduler/
    jobs/                # одна задача = один файл, вызывает services
  texts/                 # шаблоны сообщений (подготовка к i18n)
migrations/  tests/  deploy/
```
Правила развития:
- Хэндлеры тонкие и вызывают только сервисы. Сервисы ничего не знают о Telegram и тестируются отдельно.
- Новая функция = новый роутер + сервис + задачи + миграция; остальные модули не меняются.
- Внешние источники данных (ABL, в будущем mtgame или mos.ru) подключаются через интерфейсы-адаптеры.
- Все тексты вынесены из кода: в шаблоны, а редактируемые — в БД.

### 5.4 Модель данных (основные таблицы)
- `users` — tg_user_id (unique), username, full_name, birth_date, mtgame_url, phone, payment_details jsonb (список реквизитов: id, method phone/card, value, bank; до 5), pd_consent_at, is_admin, dm_available, status (`unregistered`/`active`/`inactive`/`anonymized`), inactive_since, created_at.
- `squads` — name, age_group, abl_team_ref, is_active, timezone.
- `squad_members` — членство (отражение группы): user_id, squad_id, status (`active`/`left`/`removed`), first_joined_at (не перезаписывается при повторном вступлении), joined_at, left_at, last_verified_at; unique(user, squad).
- `squad_roles` — user_id, squad_id, role (`player`/`captain`/`coach`); роль действует, только пока членство `active`.
- `squad_chats` — squad_id, chat_id; `squad_topics` — squad_id, purpose, message_thread_id.
- `training_schedules` — squad_id, weekday, start_time, duration, venue, valid_from/to.
- `trainings` — материализованные экземпляры: squad_id, starts_at, venue, status (planned/cancelled/moved), source (schedule/manual).
- `matches` — squad_id, opponent, starts_at, venue, stage, division, source (parser/manual), external_id, manual_override, raw_payload jsonb.
- `polls` — type (training/match/review/tournament/game_payment/custom), squad_id, ref_type/ref_id, tg_poll_id, chat_id, message_id, options jsonb, closes_at, closed_at (голосование закрыто по сроку), superseded_at (опрос устарел после переноса тренировки; действующий опрос на объект — один).
- `poll_answers` — poll_id, user_id, option_ids, answered_at.
- `duty_assignments` — training_id, user_id, status (assigned/replaced/done/cancelled), assigned_by.
- `greetings` — kind (birthday_template/holiday), text, media, target_squads, send_at, status.
- `payment_reminders_config` — squad_id, cron/rrule, next_run_at; `payment_periods`; `payment_receipts` — user, squad, period, file_id, status, received_at.
- `events` — squad_id, title, type, starts_at (без даты — только турнир), duration_minutes, duration_days / is_season / game_price (период и стоимость игры турнира), place, description, created_by, notify_group, match_id, tournament_id (матч → турнир).
- `game_payments` — squad_id, event_id (матч), amount, deadline_at, details jsonb (снимок реквизитов), created_by_user_id, collector_user_id (получатель денег), cancelled_at (заменён новым сбором), created_at. Опрос «Оплатил» — `polls` с ref_type `game_payment`.
- `receipt_requests` — squad_id, month (первое число месяца), deadline_at, created_by_user_id (NULL — по расписанию), created_at; уникальность (squad_id, month). Опрос «Отправил» — `polls` с ref_type `receipt_request`.
- `reminder_log` — уникальный ключ (kind, ref_id, offset) для идемпотентности: одно напоминание не отправляется дважды.
- `settings` — scope (global/squad), key, value jsonb; `feature_flags`.
- `audit_log` — кто, что и когда изменил.

Время хранится в `timestamptz` (UTC), пользователям показывается в Europe/Moscow.

### 5.5 Планировщик и надёжность
- Задачи идемпотентны: перед отправкой проверяется `reminder_log`, ключ уникальный. Отметка фиксируется в БД **до** отправки, отдельно для каждого сообщения: при сбое посередине рассылки сообщение скорее не уйдёт, чем уйдёт дважды. Ошибки Telegram (включая сетевые и 5xx) не прерывают задачу — сообщение считается недоставленным.
- Апдейты одного пользователя обрабатываются по очереди (`SimpleEventIsolation`): двойное нажатие не проходит один шаг диалога дважды. Изменения дежурств и тренировки выполняются под блокировкой строки тренировки; в БД — уникальность засчитываемого назначения (тренировка, игрок).
- При рестарте пропущенные задачи догоняются, если не устарели (misfire grace, например 1 час для опросов и 12 часов для поздравлений).
- Отправка соблюдает лимиты Telegram (~20 сообщений в минуту в группу, ~30 в секунду всего): retry с учётом `retry_after`.
- Таймзона планировщика — Europe/Moscow.

### 5.6 Задел на развитие
- Сервисный слой можно открыть через REST (FastAPI) для будущей веб-админки или Telegram Mini App без переписывания логики.
- Тексты централизованы, поэтому i18n добавляется легко.
- Будущие модули: статистика посещаемости и игр, интеграция с mtgame.ru (подтягивать статистику игрока по ссылке на профиль через адаптер в `integrations/mtgame/`), учёт оплат, ростеры на матч, экспорт в Google Sheets.

## 6. Нефункциональные требования
- **Производительность:** ответ на команду < 1 с (p95) при нагрузке до ~500 пользователей и ~20 составов.
- **Доступность:** автоматический перезапуск контейнеров (`restart: unless-stopped`). Простой при деплое — не больше 1 минуты: Telegram повторяет доставку webhook, апдейты не теряются.
- **Безопасность:** секреты только в `.env`/переменных окружения, не в git. Секрет webhook и случайный путь. Postgres не доступен извне. SSH только по ключам, firewall (ufw: 22, 80, 443). Права проверяются на сервере для каждого действия.
- **Персональные данные:** согласие на обработку, удаление по запросу, минимум собираемых данных, данные детей — с согласия представителя. ⚠️ **Риск 152-ФЗ:** ч. 5 ст. 18 требует, чтобы первичная запись и хранение ПДн граждан РФ велись в базах на территории РФ. Иностранный VPS с ФИО и датами рождения этому требованию формально не соответствует. Заказчик должен решить это до запуска: например, держать БД на российском хостинге, а бот — на иностранном VPS, либо осознанно принять риск.
- **Логирование:** JSON-логи без ПДн в открытом виде, ротация. Об ошибках уведомляется админ.
- **Резервное копирование:** ежедневный `pg_dump` с хранением 14 дней и копией вне VPS (S3-совместимое хранилище). Восстановление проверяется раз в квартал.
- **Качество кода:** покрытие тестами сервисного слоя ≥ 70 %. Линтеры и тесты в CI обязательны.

## 7. Развёртывание
- Docker Compose: `caddy`, `bot`, `worker`, `postgres`, `backup`.
- Миграции Alembic применяются при старте (`alembic upgrade head`) отдельным одноразовым сервисом.
- Webhook регистрируется при старте `bot` через `setWebhook` с `secret_token` и `allowed_updates` (message, callback_query, poll, poll_answer, chat_member, my_chat_member).
- CI/CD (GitHub Actions): lint → typecheck → tests → сборка образа → деплой по SSH (`docker compose pull && up -d`).
- Окружения: `dev` (локально, polling-режим для удобства) и `prod` (webhook).
- Требования к VPS: 1–2 vCPU, 2 ГБ RAM, 20 ГБ SSD, Ubuntu 24.04, публичный IP и домен.

## 9. Приёмка
Для каждого ФТ — сценарий проверки в тестовой группе-форуме:
- посторонний пользователь пишет боту → отказ, команды не выполняются;
- участника удаляют из группы → его профиль помечается в БД, команды и ответы на опросы больше не принимаются; после возвращения в группу доступ восстанавливается;
- участник, вступивший в группу до подключения бота, проходит проверку через `getChatMember` при `/start`;
- новый участник в группе не вызывает сообщений бота; по ссылке из `/invite` проходит регистрацию;
- событие, пересекающееся с тренировкой, вызывает предупреждение; встык — нет; опубликованное событие появляется в нужном топике;
- опрос появляется в нужном топике в нужное время;
- дежурные назначаются по давности последнего дежурства (вернувшийся после долгого перерыва игрок выбирается первым), новички первых 14 дней не назначаются, замена работает;
- при недоступном сайте ABL срабатывает фолбэк;
- напоминания журнала приходят за 3 дня, за 1 день и в день события ровно по одному разу, в том числе после рестарта worker;
- квитанция пересылается тренеру, статус меняется.

Критерии: все сценарии пройдены, CI зелёный, бэкап восстановлен на тестовом стенде.
